# Castcorder design

The agreed design as of 2026-11-10. Vocabulary is defined in [CONTEXT.md](../CONTEXT.md); the decisions with real trade-offs are in [adr/](./adr/). This file records everything else that was decided.

## Product

A free, open-source desktop app for recording podcasts, at `castcorder.app`. Participants talk over a live call while every machine records its own sources locally at full quality, then delivers the files to the host. It should feel like an application (install, copy link, talk), not a self-hosting project.

## Roles and access

- The host is a machine running the app. It serves all of its rooms silently whenever the app runs (one live call at a time; see "Rooms and calls"); someone at the machine joins explicitly to become a participant.
- Producers hold in-call controls: takes, the recording profile, selecting anyone's sources, password, lock, kick. Whoever is at the host is a producer. Only someone at the host grants or revokes the role, and only to a trusted device.
- Producers cannot delete tracks, change the storage location, delete the call, or appoint producers.
- No accounts. Every device generates its own key: per install for the app, per browser profile for the web. A device may be linked to a person (ADR 0005, "Persons and linked devices"): the person's devices are trusted producers in each other's rooms; a device never linked stays anonymous. Persons can become contacts ("Contacts").
- A call link is the host key plus a call secret, carried in the URL fragment.
- Per room: producer-gated (default; guests wait until a producer joins) or always open. Optional password. Lock admits trusted devices only. Kick bans a device key. Regenerating the link fixes a leak.
- Joining discloses that a producer can see and select the guest's sources. A recording indicator is always visible.

## Recording

- Tracks are raw: no echo cancellation, noise suppression, gain, or resampling. Capture uses shared mode with OS effects bypassed, at the device's configured format.
- Audio is written as PCM/WAV to local disk on the highest-priority thread, then converted to FLAC after the take.
- Each participant has one live source per kind and a set of recorded sources. A producer can record several microphones per participant (for example a backup beside the main mic).
- Video recording is optional per call and independent of live video. Webcam only. Default is a real-time hardware encode at a visually lossless bitrate; camera-native passthrough and lossless are app-only profile options.
- A device that cannot meet the recording profile reports that to the producer. No automatic fallback in v1.
- The host writes each guest's live stream to disk as received, as a safety track.
- Host storage: `<library>/<room>/<call>/<take N>/` holding raw tracks, aligned tracks, safety tracks, and timing metadata. FLAC by default for raw and aligned tracks, configurable.

## Takes

- A producer starts a take: 3-second countdown, every device starts its recorded sources and acknowledges each one. A source that fails raises a warning and never blocks the take.
- Only a producer stops a take. It otherwise continues until every participant has left. The host has a configurable maximum take length (default 4 hours, may be off).
- A participant who joins or rejoins mid-take starts recording immediately.
- Before a take each device reports free disk space; the producer is warned when a device has under about an hour's worth. Recording is never stopped pre-emptively. Devices report free disk when joining, at each take start and every minute (a browser: storage quota less usage; the host: the library volume through the disk port); the host warns producers in an amber banner and per person in People when a device holds under an hour at the recording profile's data rate (audio 384 kB/s, plus 1 MB/s with video), and the take still starts.

## Never losing data

1. Capture always writes to local disk first. The network is never in the recording path.
2. A source dropout or crash ends a segment; the track continues in a new segment when the source returns.
3. The host keeps a manifest per take of expected tracks and verified received data.
4. Any reconnection from the same device resumes missing transfers automatically, even days later. A device in no call syncs over a sync-only connection (see "Background sync"): a guest that left, an app guest in the tray, a page reopened later.
5. If the host is lost mid-take, guests keep recording locally until it returns or they stop manually.
6. Local copies are deleted only after the host confirms verified receipt. App guests keep them 7 more days; browser guests delete on confirmation.

The outbox syncs whenever the host is connected and no take is recording: audio before video, oldest take first. Sync and live traffic compete, with priority hints where the platform honours them. Transfer is our own verified, resumable, range-based protocol over the existing connection, sized to suit S3 multipart later.

Browser guests store tracks in the browser's private filesystem: persistent storage is requested (best effort), and the guest is told to return in the same browser to finish syncing. Chromium browsers and Firefox are supported targets; Safari is a medium-low priority. Chromium records on the microphone's clock (MediaStreamTrackProcessor); other browsers use an AudioWorklet fallback, with any detected drift written to the track's metadata.

## Timing

Each device continuously measures its clock offset to the host and logs it beside the samples. The host renders aligned audio tracks (offset and drift corrected, with an offset-only option) as derived files. Timing metadata is a JSON sidecar, exported as Audacity labels and Audition marker CSV; aligned WAVs carry a broadcast-wave timestamp. Video is delivered raw with timing metadata and is not aligned.

## Architecture

- Star topology through the host (ADR 0001). About 4 participants with video, 6 with reduced or no video. Audio is prioritised over live video.
- Rust throughout. A headless core does capture, recording, forwarding, and sync: GStreamer for media, str0m for WebRTC transport and forwarding.
- One Leptos client (client-only mode) runs in the browser and in the Tauri desktop shell. It talks to a core through one interface with two implementations: the native core in the app, an in-browser WASM core for browser guests.
- One shared protocol crate of typed requests, responses, and events, used by every component.
- One app for hosts and app guests. It is a user-level process that closes to the tray, with optional start at login. A `castcorder://` handler opens call links.
- The core reaches time, network, disk, and capture devices only through port crates (ADR 0003).

## Services

- Browser client: a project-hosted static site, one path per release, pinned in each call link (ADR 0002).
- Rendezvous: a WebSocket mailbox. The host holds a connection while running; guests send connection info encrypted to the host key. Deployed as a Cloudflare Worker with one Durable Object per host key, serving the client too; the Rust rendezvous shares its mailbox logic and is the self-hosted and test implementation (ADR 0004).
- Rendezvous on Cloudflare (`castcorder/worker`, workers-rs; ADR 0004). The mailbox state machine (routing, per-IP and per-host-key limits, whether relay credentials may be minted) is the I/O-free `castcorder-mailbox` crate; the Rust rendezvous wraps it in axum, the Worker in Durable Objects. Every `/ws` connection names the host whose mailbox it is for (`?mailbox=HOST_ID`; a guest joining a call that sends only `?host=` is routed by that), since a WebSocket cannot move to a Durable Object after the first frame: the host its own key, a guest, a status query or a link request the host it addresses. A scoped connection may only register as, or offer to, that host, in both implementations. The Worker refuses `/ws` naming no valid host id before touching any Durable Object, limits connections per IP at the edge (the `ratelimits` binding), and hands the upgrade to that host key's Durable Object, which holds the host's and its guests' WebSockets with the hibernation API: each connection's mailbox state rides in its attachment and its connection id in its tag, and a woken object restores them (rate-limit buckets start full again, and connection ids restart from the clock so a late answer never reaches a newer guest). The object sends no pings, so the host pings after 20 s of silence; the runtime answers without waking the object. Static assets serve `/v/<version>/`. The hello carries `stun_port: null` and the `STUN_URLS` var (`stun:stun.cloudflare.com:3478`); a host without a STUN port takes the first `stun:` URL of the hello's `ice_servers` to learn its server-reflexive address. Relay credentials (`worker/src/relay.rs`): `RELAY=cloudflare` mints Cloudflare Realtime TURN credentials (`generate-ice-servers`, secrets `CF_TURN_KEY_ID` and `CF_TURN_API_TOKEN`; every TURN URL it returns except port 53, so TCP and TLS on 443 too); `RELAY=coturn` mints coturn REST credentials (`TURN_URLS`, secret `TURN_SECRET`; the scheme shared with the Rust rendezvous in `castcorder-mailbox`), which CI exercises; `TURN_TTL` (default a day) sets their lifetime, and each `IceServer` carries `expires` since Cloudflare's usernames are opaque (the host renews by it, and so does a browser guest: at 80% of their life its call or sync-only connection takes a fresh hello naming the host, applies its ICE servers with `setConfiguration`; at the next ICE restart (`{"type":"restart"}` on the control channel asks the host for one) the guest gathers a relay candidate with the new credentials without reconnecting; the renewed credentials wait for the host's own renewal restart, which comes at the same point of the same lifetime, and the guest asks for one only if none comes by half the old credentials' remaining life; a host restart that comes first, from 60% of the guest's credentials' life on, renews them before the answer; so one ICE restart carries both renewals, since two restarts seconds apart could leave a guest on a lossy network with no working path (cast-um1)). Relay credentials go only to a guest that proves it holds a call link the host admits (cast-d74): knowing a host id is not enough to use the project's relay as a generic forwarder. The proof is HKDF-SHA256 of the call secret (salt `castcorder-relay-proof-v1`, info `relay credentials`, 32 bytes, base64url), sent as `?proof=` beside `?host=`; the host registers the gate of each call secret it admits (SHA-256 of the proof) in a `relay_gates` frame after `registered` and again whenever a link is regenerated or a room added (checked every 2 s), and the mailbox compares SHA-256 of the presented proof to those gates (`relay_proof` error otherwise, so the guest still tries a direct connection). The server never sees the secret and cannot recover it from the proof; regenerating a link retires its proof. The Durable Object keeps the gates in its storage so a woken object still answers guests, and clears them when the host registers again or leaves. Each host key may mint `RELAY_DAILY_CAP` credentials per UTC day (default 300), counted in its Durable Object's storage so hibernation and restarts do not reset it; past that, `relay_quota`. A relay that cannot mint answers `relay_unavailable`. Locally `task worker:dev` runs it under `wrangler dev` with no account. Tested: the mailbox crate's unit tests (scope, restore through JSON, relay decisions, coturn REST and Cloudflare answers, the daily cap); `task test:system:worker` runs the tier 3 system test against the Worker under `wrangler dev` (in CI), with the host idle 50 s so its Durable Object hibernates and must restore it, sync-only connections, link requests (a browser profile and a second install), the rejoin scenario (status queries), and with Docker a `--relay-only` host and a forced-relay guest through coturn on credentials the Worker minted with a 30 s `TURN_TTL`, which the guest renews before they expire and keeps its call; `task test:worker:relay` checks the credentials and the daily cap across a `wrangler dev` restart, and Cloudflare Realtime TURN for real when `CF_TURN_KEY_ID`/`CF_TURN_API_TOKEN` are set (skipped otherwise, also in CI until the deploy secrets exist).
- Relay: Cloudflare Realtime TURN when deployed, stock coturn when self-hosted and in CI, with short-lived credentials minted by the rendezvous per host key. STUN: `stun.cloudflare.com`.
- Both are rate-limited per host key and per IP address. Charging may attach to the host key later.
- Relay badge (cast-9ok). The host tells everyone in the call whether each connection goes through a TURN relay: from str0m's selected candidate pair (each second), relayed when its local address is one of the host's relayed addresses or its remote address a relay candidate in the guest's offer or answer (`HostEvent::GuestPath`, logged as "connection path"). `Event::Relayed` goes to everyone joined, the participant included, when first known and on every change, and every participant's latest to a newcomer. A relayed participant's tile, and their own, show a "Relay" badge at the top right, and producers' People rows a Relay chip; direct connections show nothing. Tested: transport simulation (direct pairs say so; a relay-only host's say relayed), SDP parsing, the browser e2e (direct guests show no badge) and the relay tier (guests forced to `iceTransportPolicy=relay` show the badge on each other's tiles and their own).
- Video over a relay (cast-btf). Raw video is large (about 8 GB an hour at 1080p) and a relay's bytes are billed to the project, so the host never pulls video from a guest whose connection is relayed or whose path is not known yet; the guest's video waits in its outbox for a direct connection and syncs then, with no opt-in (an external user cannot consent to the project's spending). Audio and logs sync over a relay as usual. In `castcorder_core::library::Puller`, `set_video_allowed(false)` leaves queued video queued, parks a video transfer under way (what arrived stays on disk and it resumes later) and counts as idle, so a held video never keeps a call or a sync-only connection waiting; the host sets it from the connection path on every poll, for call guests and sync-only connections. `GET /status` reports `video_waiting_for_direct` per guest and per sync-only connection, and the Relay badge's tooltip says video waits. Tested: `relay_video_hold_sim` (video queued while relayed, audio and logs sync, video syncs once direct; a transfer under way pauses and audio is not stuck behind it) and the host's path rule.
- Relay metering. Every relay credential is named `<expiry>:<host id>`, for the host and for its guests, so coturn's Prometheus exporter (`prometheus`, `prometheus-username-labels`) reports relayed bytes per host key. The rendezvous scrapes it (`--turn-metrics`), adds the growth of each counter to the host key's day (a new or reset counter counts in full) and keeps a 30-day ledger in one JSON file in `--data-dir`, written atomically so a restart neither forgets nor re-counts. coturn counts a session when it ends (deallocated or expired), so usage lags a live allocation by up to the credential TTL. A host key at or over `--relay-budget` (bytes per rolling 30 days) gets no relay credentials: `registered` and the guest's hello carry `relay_error: relay_quota: ...`, the host logs it and asks again in 15 minutes, guests log it and, when their connection needs a relay, see a call note that says so and suggests another network (cast-gln), and direct connections keep working. coturn's `user-quota` and `max-bps` cap allocations per credential and bandwidth per session (coturn counts them per username, not per host key). Operators read usage per host key with `GET /usage` on the loopback-only `--admin` listener or `castcorder-rendezvous usage --data-dir DIR`. Tested: ledger and budget unit tests; a seeded ledger refuses a real host and guest in `task check`; in the relay tier a relayed call's bytes reach the ledger through real coturn, and the rendezvous restarted with a 1-byte budget refuses with `relay_quota`, and a guest forced onto the relay is shown the note.
- Structured logs in every component, correlated by call, device and take, kept locally in rotating files. For now, guests' logs sync automatically to the host as files through the outbox, disclosed at join, and land beside the call's takes. No third-party destination.

## M0 results

All five spikes returned "go with caveats". Proof code and full findings are in `castcorder/spikes/<name>/FINDINGS.md`. What they settled:

- **Transport: str0m.** Three Chromium guests exchanged forwarded audio and video through a str0m host, with a verified data-channel transfer. str0m does ICE only, so the host needs its own STUN and TURN client. Leaves are detected by an application heartbeat (about 1 s), not ICE (14-22 s). One video codec per call (VP8). Per-guest video step-down means guests publish two simulcast layers and the host picks one or drops video.
- **Media engine: GStreamer.** One capture teed to a byte-identical WAV and a processed Opus branch; a stalled live branch does not affect the recording. We keep our own WAV writer (header rewritten each second, RF64 past 4 GiB, repair on startup). Video records to Matroska, which survived a hard kill intact. Device loss is detected by the device monitor plus a no-data watchdog.
- **Transfer: bao-tree.** Verified, resumable transfer natively and in browser WASM. 16 KiB chunk groups, 1 MiB units, 64 KiB frames, 8 MiB S3 parts. The hash is computed while recording. Browser storage writes must be batched per unit.
- **Browser recorder: Rust and Leptos work.** Raw and processed opens of one microphone coexist in Chromium; the raw one is lossless. Recording is a float32 WAV patched in place, recoverable after a browser kill. One 68-line JS file is unavoidable.
- **Protocol: the typed protocol crate.** Leptos server functions do run over a data channel but fit the two-core design and server-pushed events poorly.

What they changed or left open:

- **Browser capture clock.** An AudioWorklet runs on the output device's clock, and a 150 s soak showed Chrome inserting or dropping 10 ms blocks as it drifts from the microphone. This must be fixed before M1, likely by capturing on the microphone's clock in Chromium, and any insert or drop must be recorded in timing metadata.
- **Start-up gap.** A freshly opened virtual microphone delivered nothing for about 2 s. Acceptable if not easy to avoid: producers wait for everyone to be back before talking.
- **Unverified:** Firefox and Safari end to end (medium-low priority), any relayed or lossy network path, Windows and macOS capture, and virtual webcams on CI runners.

## M4 live video (part 1: live only)

- **Sending.** A browser guest opens its camera with its own `getUserMedia` (a missing or refused camera never costs the microphone) and sends it on one video transceiver created at connect with two VP8 simulcast encodings: `h` full size up to 800 kbit/s, `l` half size up to 150 kbit/s. Turning the camera off or on swaps the sender's track (`replaceTrack`, null when off) and releases or reopens the device, so it never renegotiates. It also says so (`CameraState` on "control", sent after every join and on each change; the host keeps the latest per participant, relays it, and replays it to latecomers), and the others' tile for it shows the camera-off avatar while it is off, whatever the browser reports of the silent track (a track unmuting does not clear it while it is signalled off). Headless Chromium and Firefox both send both layers.
- **Forwarding.** Per receiver, every 250 ms, the host reserves the forwarded audio's measured rate, then gives every video track its lowest live layer while it fits 90 % of the receiver's TWCC estimate, then upgrades one step at a time (stepping up needs 25 % to spare and must stay admitted for 3 s, except a source's first layer; stepping down is immediate); otherwise that receiver gets no video. Layer rates are smoothed (a quarter of each 500 ms window's rate) from a nominal prior per rid (l 100, h 800 kbit/s), so video starts at once and an encoder's swings do not flip layers. A layer silent for 2 s counts as not sent. A new layer is asked for a keyframe (PLI per rid: a simulcast track has no stream without one) and takes over at that keyframe, with RTP times shifted to continue the outgoing stream. The estimator is told to sustain what the next upgrade needs and probe for the best layers. str0m sends audio unpaced, ahead of queued video.
- **UI.** Each remote participant gets a tile (video plus audio) labelled with the participant's display name (the host sends everyone the participant list; the stream id `<name>-<participant id>` keys it); the guest's own camera shows in a muted preview tile. The host's native participant stays audio only.
- **Tested.** A simulation through str0m's real estimator on `SimNetwork` with capacity limits: an unlimited receiver climbs to `h`, one at 500 kbit/s gets `l`, one at 120 kbit/s gets no video, and all keep every audio frame. The browser test decodes each other's video in Chromium and Firefox, sees two layers sent, and toggles a camera without an offer. A host started with `--bandwidth-cap 250` (a configured cap on the estimate the allocation uses, not network shaping) makes real Chromium and Firefox guests settle on `l` (320x180) with audio flowing.
- **Open.** Native camera capture; Safari; real lossy and congested paths; CPU cost of two encodes on weak machines.

## M4 video recording (part 2: browser guests)

- **Profile.** Whether a call records video is a room setting (`RoomAction::SetRecordVideo`, the producer's "Record video" button, `castcorder-host --record-video true|false`), saved in `room.json`, default off. A take carries it in its status (`TakeStatus::Recording { take, video }`), so a change applies from the next take and mid-take joiners get it too.
- **Recording.** A browser guest whose camera is on records the camera track itself with MediaRecorder: WebM, VP9 where supported (Chromium) else VP8 (Firefox), at 0.3 bit per pixel per frame, 4 to 60 Mbit/s. Every second a chunk (a `Blob`) goes to the storage worker, which reads it with `FileReaderSync` and appends it to `tracks/<take>-<ms>-cam.webm` with one OPFS write and flush, rewriting a JSON sidecar. A camera turned off mid-take ends that video track; turned on again, a new one starts. A crash leaves a valid WebM prefix (unknown-size elements), finalised as `recovered` at the next scan. Kept as WebM on the host (it is Matroska; `ffmpeg -c copy` adds duration and cues for editors).
- **Resolution.** The recorded track is the camera as opened for the live call (640x360 ideal); raising the capture size needs `scaleResolutionDownBy` on both simulcast layers first, or the `l` layer and the bandwidth-cap test change. Open.
- **Timing.** `<track>.timing.jsonl` with the audio header (`sample_rate` 0), the clock exchanges, `video_start` (device and host time, codec, size, bitrate), one `chunk` per write (offset, bytes, device and host time, the recorder's timecode) and `video_end`. Video is not aligned.
- **Sync.** The webm, sidecar and timing file are `SourceKind::Video` outbox items; the guest offers in sync order and the host pulls every audio item first. On the host: `<call>/takeNN/takeNN_<who>_cam.webm` (`_<who>-2_cam` for a second camera run) beside `.json` and `.timing.jsonl`. Only audio completions trigger alignment. A 48 MiB video syncs with under 8 MiB of heap growth (`castcorder-core/tests/video_memory.rs`).
- **Cannot meet profile.** A browser whose MediaRecorder supports neither codec sends `Request::ProfileUnmet` once per take; every producer gets `Event::ProfileUnmet` and sees it in the panel. The take, and that guest's audio, go on.
- **Tested.** Take 3 of the browser test records video in Chromium and Firefox: each webm has an EBML header and DocType webm, ffprobe decodes VP9 (Chromium) or VP8 (Firefox) of the expected length, the timing chunks tile the file and the recorder starts within tens of ms of the take start; per device the host verified all audio before any video; A's audio stays bit-exact in Chromium. In Chromium guest B's `isTypeSupported` is replaced to say no, and the producer sees B's warning while B's audio syncs. Takes 1 and 2 (default off) have no video.
- **Open.** In Chromium, reopening the camera mid-take stalled the page's raw audio capture once by 40 ms (seen with fake devices; the Firefox run toggles the camera instead); capture resolution above the live request; Safari.

## M5 desktop shell (part 1)

- **Host as a library.** `castcorder-host` is a library plus the unchanged binary: `castcorder_host::start(Config, on_link)` runs a host in-process and `Running::stop` finishes the host microphone take and the safety tracks, then ends the listeners, the rendezvous connection and the call thread so the ports are free. Both the binary and the app parse the same host flags (`Config::apply_args`).
- **App.** `castcorder-app` (Tauri 2, feature `desktop`; `task app`) starts the host with the app, and its window shows the producer page (`http://localhost:<port>/`), where the person at the host joins explicitly as in a browser. Closing the window hides it to the tray and the host keeps serving; tray Quit finishes and stops it. "Start at login" is a tray toggle (tauri-plugin-autostart, launches `--hidden`), off by default. A host that cannot start (a port in use) shows the reason in the window.
- **Links.** `castcorder://<rendezvous>/<path>#<host-id>.<call-secret>` opens the matching `https://` call link in a call window, after the fragment validates as a call link (tolerating `%23` and trailing slashes). The app registers the scheme per user at start (`--no-register` skips it) until installers do; tauri-plugin-single-instance hands a second launch's link to the running app instead of starting a second host.
- **Tested.** In `task check`: the app's host control starts the host on OS-picked loopback ports, `GET /role` answers, a str0m guest signs its offer for that host id and connects over UDP, then the host stops and starts again on the same ports; the link mapping and flag parsing are unit tests. `task app:check` (CI job `app`, under xvfb on Linux) adds clippy for the shell and `castcorder-app --smoke`: the hidden window loads the producer page, `APP_READY`, clean stop.
- **Installers.** `task app:bundle` (and `.github/workflows/release.yml`, on a `v*` tag or workflow_dispatch) runs `cargo tauri build --config tauri.bundle.conf.json`: NSIS and MSI on Windows, `.app` and `.dmg` on macOS, `.deb` and AppImage on Linux, all unsigned. The trunk-built client ships as the `client` resource and the in-process host serves it from there (beside the exe, `../lib/Castcorder/`, or `../Resources/`). Every release build has `native-capture`. The Windows installers bundle a trimmed, LGPL-only GStreamer (`task app:gst:stage`, `scripts/gst_bundle.py`: the 11 plugins capture, live and playback use and the DLLs they import, with their licences and a source notice; about 12 MB unpacked): the libraries beside the exe, the plugins in `gstreamer-1.0/`, which castcorder-capture-gst scans at init. The Windows installers also ship the MSVC runtime app-locally (a clean machine lacks it; `scripts/check_install_dlls.py` fails the smoke on any imported DLL that is neither in the install nor a system DLL, since the hosted runner has the runtime in System32). The macOS build is one universal (x86_64 and arm64) `.app` with the same trimmed set from the official universal GStreamer.framework (about 34 MB, both slices): the libraries in `Contents/Frameworks`, the executable's rpath (`build.rs`), and the plugins in `Contents/Frameworks/gstreamer-1.0`, copied unmodified (every framework library is linked as `@rpath/<name>`); `Info.plist` adds the microphone and camera usage descriptions macOS requires. The `.deb` (built on Ubuntu 24.04 for GStreamer 1.24, so glibc 2.39 and newer) depends on the distro's GStreamer packages. The AppImage carries the GStreamer libraries the executable links (the build machine's 1.24) but no plugins, and AppImage tooling patches the built-in plugin path out of its libgstreamer, so castcorder-capture-gst scans the distro's plugin directories when no plugin was found: native capture there needs the system's base, good and PulseAudio plugins at 1.24 or older (GStreamer rejects plugins newer than its core), so on a distro with newer GStreamer the AppImage has the webview microphone only and the `.deb` is the supported route. `castcorder-app --smoke-gst` checks that GStreamer initialises and finds every element; the Windows smoke runs it with no other GStreamer on PATH and the macOS smoke with the build's GStreamer.framework moved away (`scripts/check_app_dylibs.py` also checks every library is the system's or in the `.app`, in both slices), and both check every plugin loads from the install. A tag creates a draft GitHub Release with the installers; the smoke run covers the installed app on Windows, macOS and Linux (the `.deb`, and `--smoke-gst` from the AppImage on a runner with the system GStreamer).
- **Native microphone at runtime.** In a build with `native-capture`, the person at the host joins and leaves the call with an input GStreamer's device monitor lists, from the producer page ("Microphone on this machine") or through `HostControl::join_native`/`leave_native`; `--participate` is the same join at start. The page uses `GET /native`, `POST /native/join` and `POST /native/leave`, answered only on the localhost listener with a loopback `Host` and an `X-Castcorder-Native` header (a cross-site page cannot send it without a preflight). Joining mid-take records from the join; leaving mid-take finishes that take's microphone files first and closes the input. Tested in `task test:gst`: a WAV file through the capture port joins at runtime twice and each take's raw track is bit-exact.
- **Tray status.** The tray shows a one-line status (`2 guests, recording take 3, syncing 1`) as a disabled menu item, in the tooltip, as a `REC <take>` title (macOS) and as an icon with a red dot while a take records. The app polls `HostControl::live_status` once a second (a `Command::Live` to the call thread: guests, recording take, last take, guests with an outbox still syncing) and touches the OS only when it changed. A "Rooms" submenu lists every room (the live one marked) with its own "Copy call link", which puts that room's link on the clipboard (tauri-plugin-clipboard-manager; a room with no link yet is greyed and says so; the list follows the host's rooms, refreshed every few seconds) (cast-7jv). There is no Regenerate in the tray: it silently broke links pasted into invites. Replacing a room's link is in its menu on the home ("Replace link..."), which asks first and says the old link stops working for everyone (guests in the call stay). Copying needs a rendezvous (a call link). Tested in `task check` through host control against a real host (guest joins: 1 guest; take starts: recording) and in `task app:check` (`--smoke` asserts the snapshot answers).
- **Open.** App guests use the browser client in the call window rather than the native core; updater; signed and notarized macOS builds.

## Rooms and calls

- **Layout.** The library root holds the host key (`host-identity.key`), the LAN certificate (`host-cert.pem`, `host-key.pem`) and the person (`person.json`, see "Persons and linked devices"). `<library>/<room>/` holds `room.json` (settings, trusted devices, producers, bans) and `call-secret` (the room's call link), and one folder per call, `<YYYY-MM-DD>[-N]` (UTC start date) with `call.json` (started, last active), its `takeNN/` and guests' `logs/`. The host's own log is in `<library>/logs/`. A folder from before rooms (`takeNN/` beside `room.json`) becomes a room with that one call at start: its takes and logs move into a dated call folder, idempotently (a move cut short finishes next start).
- **One host, many rooms, one live call.** The rendezvous offer's secret picks the room; LAN pages name it with `?room=` (none: the live room, else the default room, `--room`; `--call` is its old name). A call is live while anyone is in it or a take records. An offer for another room gets `waiting:` and the page asks again, so a guest on a room that is not live waits in the lobby. With nothing live, the first one the room admits opens it: in a producer-gated room a producer or the host machine, in an open room anyone.
- **Routing.** The first one in opens the room's most recently active call if it was active less than the idle gap ago (`--idle-gap` minutes, default 120), else a new call. The open call is marked active every minute while live and when it empties, so a rejoin, even after a host restart, lands in the same folder and take numbers continue. Routing reads "now" through the clock port (`Config::clock`).
- **Choosing a call.** In a call, producers see the room's calls (`Event::Calls`) and can move everyone into a new call or a past one (`RoomAction::NewCall`, `ContinueCall`), only while no take records and every device has synced. Before joining, a remote producer who was in a past call continues it by naming it in its offer (see "Rejoining"). The host machine's home does it before joining: a past call is marked the most recently active, a new one is made, and the next join lands there.
- **Per-call tracks, one outbox.** Each device is told its call (`Event::Call`) after Joined and on every move, and keeps its tracks (and log files: the worker starts a new one when the call changes) under that call's scope (`<host>/<room>/<call>`). Whenever it is connected to any call of that host, its outbox offers every pending item of that host: this call's and those from before rooms with `OfferTrack`, another call's with `OfferCallTrack` naming its room and call. Order as always: audio, video, logs; oldest call, then oldest take first. The host records every device it tells a call in that call's `devices.jsonl` and files an `OfferCallTrack` into that call's folder only if the connection's verified device is listed there (or, for a call from before the list, named in its manifests); otherwise it refuses and the item stays on the device. The check reads only that call's folder, never which call or room the device is in now, so a later sync-only connection can use it as is.
- **Home.** The host machine's own page with no query (the desktop window) lists every room with its call link (Copy, New link), Start new call, Join (the room's lobby, `/?room=NAME`, with this page's microphone or the machine's native one, which mutes call-only) and its past calls with date, takes, Open folder and Continue this call. It uses `GET /rooms`, `POST /rooms`, `/rooms/link`, `/rooms/call`, `/folder/open` and `/native/mute`, answered only on the localhost listener with the native header.
- **Tested.** Unit: routing (recent within the gap, beyond it, explicit choice), call ids, migration and a migration cut short. `castcorder-app/tests/rooms.rs`: two rooms, the second waits while the first is live, a rejoin keeps the call folder and take numbers, a join after the simulated gap makes a new call, the other room then opens its own. Browser (`lib/rooms.mjs`, Chromium and Firefox): the home makes a room and copies its link, a guest on it waits, the producer joins from the home, leave and rejoin keep the call, a new call gets a new folder, the home lists both and Continue picks the old one; a guest that left mid-take joins a later call and its take lands in the old call's folder and leaves OPFS, while a track it claims for a call it was never in is refused and kept. Core (`cross_call_sim.rs`): tracks recorded in an old call file into that call verified and leave the device, audio first and oldest call first; a call the device was never in refuses its track; the device list survives a restart and a torn append. gst: muting the native microphone silences the encoder input while the recording stays bit-exact.
- **Open.** A take of another call completed this way (or over a sync-only connection) is not aligned automatically yet.

## Background sync

A device syncs whenever it and the host are both online, not only while it is in a call, so a trusted guest can leave at will and its files follow as bandwidth allows.

- **Sync-only connection.** The same WebRTC wire contract with the two data channels alone: no audio or video m-line (an offer with one is refused, `Host::accept_sync`), never sent anyone's media, so never renegotiated with. The offer says so (`sync_only` in the sealed offer, `"sync":true` on a LAN `/offer`) and is signed by the device key like any offer. It sends no Join and is not a participant: it neither opens, holds nor waits for a call and is never counted as anyone in one (the tray's guests, "live", the one-live-call rule), though the tray counts it as syncing.
- **Admission.** By device key alone, through any room's link (or `?room=`): no lock, password or producer gate applies, since it joins no call. A device kicked from that room is refused (`kicked:`; `Room::admit_sync`, read from that room's saved state when another room is loaded). It is accepted beside the live call of any room.
- **Authorization.** Its only request is `OfferCallTrack`; anything else is refused. Each item is checked against the call it names exactly as for a connection in a call (`call_library`: the device is in that call's `devices.jsonl` or its manifests) and refused if the device was kicked from that call's room; a refused item stays on the device. Items from before rooms name no call and wait for a join.
- **One library per folder.** Items file into their call's folder under the key `<room>/<call>`: the open call's library when it is that call (`CallSet::open_key`), else one kept for it. When a call opens or closes while sync-only connections exist, the library moves between the two slots, so one folder never has two manifest writers.
- **Below live media.** A sync-only connection asks for nothing new while a take records or a guest in the call is still syncing its own outbox; data already asked for still lands. Between connections there is no finer priority: the live call's media is on its own peer connections.
- **Browser guest.** After Leave, and when a page opens without joining (the host's own home excepted), the page lists the outbox for this host; with anything deliverable it connects sync-only (no microphone or camera) and offers it, retrying with the usual backoff while the page is open. The lobby's `#sync-state` shows the files left and then the outcome (all delivered, some refused and kept, or the device refused). Once nothing deliverable is left the connection closes; joining stops it. Test hook: `window.__castcorderHoldSync` holds it unconnected.
- **App.** Closing a call window leaves the call (its Leave button) and hides the window: its page goes on syncing from the tray. The last `castcorder://` link opened is remembered in the app's data folder (`last-call-link`) and reopened in a hidden call window at every start, at login too, so its page finishes the sync without joining.
- **Tested.** Transport sim: a sync-only guest beside a call gets no media and no renegotiation, its data channel round-trips, a media offer is refused. Core sim (`cross_call_sim.rs`): a sync-only puller files by key with no call open and carries on when that call opens midway. Room unit: lock, password and gate do not apply; a banned device and a bad id are refused. App (`tests/sync_only.rs`, real host): a guest records, leaves, another room's call goes live, the guest's sync-only connection is admitted beside it (not counted in it) and its take lands verified and bit-exact; other requests and a call it was never in are refused; once banned its items are refused. Browser (`lib/rooms.mjs`, Chromium and Firefox): a guest leaves mid-take and its page shows the take waiting; once another room is live the take lands over a sync-only connection and leaves OPFS while the foreign track is kept and reported; a guest kicked mid-take is refused sync-only and keeps its take.

## Rejoining

Anyone who has been in a call, and was not kicked, sees the rooms and calls they took part in, with live status, and can rejoin them (cast-zr8).

- **The list.** Each device keeps it itself, so it shows with the host offline: a browser profile in localStorage (`castcorder.rooms`, per origin), remembered whenever the host tells it its call (`Event::Call`): the room's page (the call link, or a LAN page with `?room=`), its host, and each call it was in. The lobby shows it as "Rooms you joined": a card per room (`#my-rooms li[data-room]`) with a status chip, who is in the call, Rejoin, and its calls. The host machine's own page remembers nothing (its home lists every room). The app's list is its call window's (the browser profile that holds its device key): the home links `castcorder://rooms`, which shows the call window, or reopens the last call link in it, whose lobby lists them; with no call link remembered there is nothing to list.
- **Status.** A status query is a sealed offer marked `status` (castcorder-link `OfferPlain::status`; `"status":true` on a LAN `/offer`) whose proof signs a fresh random nonce instead of an SDP. Like a sync-only connection it is admitted by the device key alone, but it opens no connection: it never opens, holds, waits for or counts toward a call and never loads a room (other rooms are read as saved). It needs no call secret, so a regenerated link does not lose the room: the host answers (`AnswerPlain::Status`, `HostStatus`) for every room the device was in (`Room::membership`, the old id's record for an upgraded device): live, busy (another room is live), the call a join lands in (the live call, else what routing would pick, else none), who is in the live call by name, whether the device is a producer of the room, the room's call link if the device is trusted, and only the calls it was in (each call's `devices.jsonl`, read without opening that call's library). A room that trusts the person the query's certificate vouches for counts that person's trust (cast-40e.11): the device is a trusted member, and a producer when the person is one, even if it never joined the room or joined while no producer was there. A device the room never saw is otherwise told nothing; a kicked one only that it was removed. The lobby asks each host once when it shows, after Leave and every 20 s while visible; a host the rendezvous cannot reach shows "Host offline". The call thread decides each room's membership and the live room's state; reading the rooms' call folders (each call's `call.json`, take folders and device list) happens on a thread of its own, as for the producer page's Rooms list, so a library of many rooms and calls (about 15 ms for 50 rooms of 20 calls on Linux, more on a slow disk) never stalls the live call (cast-0af).
- **Archive (cast-bc4).** Old calls can be hidden from the lists without touching a recording. On the host machine's home, a past call has Archive (not while someone is in it): the host sets `archived` in the call's `call.json` (`POST /rooms/archive`, `Running::archive_call`), the call leaves "Past calls (N)" and a per-room "Show archived (k)" lists it again with Unarchive. Routing ignores the flag (a join still lands where the gap rule says), and Continue this call restores the call. On a device, the same in "Rooms you joined": a call's Archive is local to that browser (`archived` on the remembered call; never the current call), with Show archived / Unarchive; the host and other devices are unaffected. Only the host machine archives for the host; a producer elsewhere cannot (decided with the bead: the host's list is the host machine's).
- **Rejoin.** Rejoin opens the room's page (or joins at once on that very page) and lands in its current call; normal join rules apply (a gated room waits for a producer, a locked one needs trust, the password). A past call is rejoined by naming it in the offer (`OfferPlain::call`, `"call"` on `/offer`; the page's `?call=`): after the usual admission it lands there if it is the room's current call; else a producer of the room who was in that call continues it (the host machine counts as one) while the room is not live, and in a live room lands in the live call, whose in-call Continue then applies (no take recording, everyone synced); anyone else is refused `not_current:` and their next Join takes the current call. The row offers Rejoin this call on the current call, Continue this call to a producer while the room is not live, else says a producer can continue it.
- **Removed.** A `kicked:` refusal (joining or syncing) marks the room removed on the device: it stays listed, says Removed, and offers no way back.
- **Tested.** Unit: membership (member, removed, producer, an upgraded device's old record); the wire shapes; the rendezvous passes a status query with a stale secret to the host. App (`tests/rejoin.rs`, real host): status for an unknown device, while in the call and after, who is in, the current call after the home starts a new one, only the calls the device was in, a call that does not exist refused `not_current:`, the host machine continuing a past call that others then join, a removed device, and a busy room. Core (`cross_call_sim.rs`): the device list read without the library, a torn tail ignored. Browser (`lib/rejoin.mjs`, Chromium, through a rendezvous of its own): a guest that left lists the room live with who is in it, across a reload; Rejoin and Rejoin this call land in the current call; a past call that is not current is refused for a guest and the next Join takes the current call; once granted the producer role it continues the past call; a kicked guest's room says Removed with no rejoin; with the host stopped, a reloaded page lists the room as offline. `castcorder-app` deeplink: `castcorder://rooms`.
- A guest that is not trusted keeps only the link it joined with: after the link is regenerated its room shows "Link changed" and "ask the host for the new link", with no Rejoin (the status answer says only that the link the query came through is no longer current, no room details; cast-lot).
- **Open.** A call from before the device list is not listed by status (its manifests are not scanned).

## Persons and linked devices

A person owns devices through a person key (ADR 0005, cast-40e.1). Contacts, presence, contact links, invites and revocation build on it later (cast-40e.2 to .6).

- **Person key.** Every app install makes a person on first start (`<library>/person.json`: the person key's Ed25519 secret, the person's display name, this device's name, this install's certificate and the devices linked from here; castcorder-host `person`). The person id is `p` and 40 hex digits of the key's SHA-256, never mistaken for a device id (`k...`). Losing every app install of a person loses the person.
- **Certificate.** The person key signs a device key: a domain tag, the person key, the device key, the kind (app or browser) and when (castcorder-link `person::DeviceCert`); names are not signed, so renaming needs nothing new. An app install's certificate is for its host key; a browser profile's for its WebCrypto key.
- **Linking.** On any app install of the person, "Link a device" (the home's "You" card, `POST /person/code`) makes a one-time link, single use for 10 minutes: `https://<rendezvous>/v/<version>/#link.<host-id>.<secret>` through the rendezvous once registered, and `https://<lan-ip>:<port>/#link.<host-id>.<secret>` to each LAN page. The new device sends a link request (`OfferPlain::link`, its proof signing a fresh nonce) sealed to that host key, through the rendezvous mailbox or the LAN page's `POST /link`. The first device to use the code claims it, bound to its key, and asks again every second or so until someone at the approving device approves or declines it, by its name and fingerprint (8 hex digits of its device id, shown on both). Approved, the next request gets `AnswerPlain::Link(Granted)`: the certificate, the person's name, and for an app install the person key (only ever inside the sealed answer, never from an HTTP endpoint).
- **Why these paths.** A link code works like a call link: the host key in it authenticates the answering device and the seal hides the contents from the rendezvous, so linking needs no new service, connection type or trust anchor. The LAN path lets two installs on one network link without a rendezvous; its TLS certificate is not checked, since the seal does that job.
- **An app install.** Pasting a link into the home ("Link this app", `POST /person/join`) links it in the background; once approved it replaces its own person with the one it joined (only while it has linked no device itself, which would be orphaned). Its rooms then belong to that person.
- **A browser profile.** Opening a link shows "Link this browser": the request goes through the page's own origin (the rendezvous mailbox for a `/v/` page, else the LAN host's `/link`). It keeps only the certificate and the person's name (localStorage `castcorder.person`), never the person key: its own key is a non-extractable WebCrypto key, and a person key kept as bytes in page storage would be the weakest copy. So only app installs link more devices.
- **Rooms belong to the person.** Every offer, status query and sync-only connection of a linked device carries its certificate (`cert` in the sealed offer or the LAN `/offer` JSON). A host whose own person it names, for the very key that signed the offer's proof, treats the device as the owner's (castcorder-host `room`, `Seat::owner`): it always enters, like the host machine (no password, lock, producer gate or ban; unless revoked, see below), it is trusted and a producer, and a status query lists every room as one it may rejoin as a producer. It is not the host machine, so it cannot appoint producers. Owner is decided per offer and never saved in `room.json`.
- **Tested.** Unit: certificates (bound to device, kind, time and person; JSON shape), link codes (round trip, not a call link), the person store (made once, survives a restart, a copied library makes a new person), linking (pending until approved, only the claimant, declined, expired, forged, a browser never gets the key, an app adopts the person, revocation: not owned, not a person's trust, not linked again, carried to an app linked later, kept across a restart), owner seats in the room, and a revoked device's room trust dropped (also under its old id; a kick stays). `castcorder-app/tests/person.rs`, two app installs with their own libraries: B links to A over A's LAN listener with A's approval and holds A's person after a restart; its own key offers to A's producer-gated, empty room through A's LAN listener: without the certificate (or with one for another key) it waits, with it it enters and starts a take as a producer; once A revokes B it waits again. A second test: a revoked device that was a trusted producer of A's locked room is told by a status query it is neither, then kept out (`locked:`), and `room.json` is saved without its trust. Browser (`lib/homelink.mjs`): Remove on the linked browser asks once more, then the device leaves the list.
- **The app's call window.** It is a browser profile of its own, and links itself to its install's person (cast-40e.7): each time the app makes the window it asks its host for a link code approved in advance (`Running::call_window_link`, only once registered with a rendezvous) and gives the window a script that sets `window.__castcorderAutoLink` on pages of the rendezvous origin only (another host's LAN page in the window never sees it). An unlinked profile on a `/v/` page uses it once, through the mailbox like any browser link, and is granted at once with nobody asked; offers and status queries wait up to 5 s for it, so the first join already carries the certificate. Such a code links only a browser profile (never an app install, which would get the person key), is used once, replaces an unused one and lasts while the app runs. It shows in the devices linked from that install.
- **Revocation.** Settings > You and your devices has Remove on each device linked from this install (pressed twice: "Remove for good?"; `POST /person/revoke {"device"}`, host machine's page only). The person key signs a revocation (castcorder-link `person::Revocation`: a domain tag, the person key, the device id, when) and the install keeps it in `person.json` (cast-40e.6). From then on the device is not the owner's here (its certificate no longer makes an owner seat), a room's trust of the person does not reach it, its own record in each room (trusted, producer) is dropped and saved when it next offers, a status query tells it neither trust nor producer, and it cannot be linked again. The install cannot revoke itself. Revocations travel to the person's app installs linked later (in `LinkGrant`, kept only if signed by that person key) and to contacts with every presence ping and answer (`PresencePing::revoked`, `PresenceAnswer::revoked`): a contact keeps those its contact's person key signed, drops that install from the contact's devices, refuses its presence pings and contact links so it is never learned again, and treats it as revoked in its own rooms. The person's other app installs learn it with the next sync ("Shared across the person's installs"). Not yet: a browser profile, holding no person key, cannot revoke.
- **Open.** The devices linked from one install are listed only there. The linking UI has no browser e2e yet (cast-40e.8).

## Contacts

Two persons become contacts when both agree (ADR 0005, cast-40e.2); presence, contact links and invites build on it (cast-40e.3 to .5).

- **Contact code.** "Add a contact" on the home (`POST /contacts/code`) makes a one-time contact code, single use for 10 minutes, shaped like a link code: `https://<rendezvous>/v/<version>/#contact.<host-id>.<secret>` once registered, and `https://<lan-ip>:<port>/#contact.<host-id>.<secret>` to each LAN page. It is not a contact link (CONTEXT.md "Contact Code"). A browser that opens one says to paste it into the app.
- **Pairing.** The other person pastes it into their app's home ("Add", `POST /contacts/add`). Their install sends a contact request (`OfferPlain::contact`, its proof signing a fresh nonce, and its own install certificate in `cert`) sealed to the host key the code names, through the rendezvous mailbox or the LAN page's `POST /contact`, and asks again every second or so. The first install to use the code claims it, bound to its key; the request must carry that key's certificate, of an app install, of another person. It waits until someone at the maker accepts or declines it, by the asking person's name and the install's fingerprint. Accepted, the next request gets `AnswerPlain::Contact(Accepted)`: the maker's install certificate and person name. The asking side keeps the maker only if that certificate is for the very host key the code names (the one the answer was sealed with), which pins the person key to the install the code came from.
- **Both sides agree.** The maker agrees by making and sharing the code and then accepting the request (so a leaked code cannot add a stranger); the other person by using the code.
- **What is kept.** `<library>/contacts.json` (castcorder-host `contact`), per contact: the person key (what certificates and revocations verify against), the name they gave, a nickname only this install uses, the certificates of their app installs learned so far (each device key is a mailbox: where presence pings and contact links will reach them), and when they were added. Pairing an existing contact again updates its name and installs and keeps the nickname.
- **Shared across the person's installs (cast-40e.9).** Each app install keeps the person's other app installs it knows by host key (`person.json` `installs`: those it linked, the one that linked it, and those they told it about; never a revoked one) and pings them with the contacts' presence pings, on the same board and timing (appearing offline is to contacts only). Between two installs of the same person, a ping and its answer carry what each knows (`PresencePing::sync`, `PresenceAnswer::sync`: `OwnSync` with the contacts, the removed ones with when, and the installs) and the person's revocations, which the other keeps if its person key signed them. Merging: a contact the other has and this one does not is added; for one both have, their installs are joined (only certificates of app installs its own key signed, never a revoked one) and the later change of name or nickname wins (`updated_ms`); a removal is kept with when, and wins over a contact not changed since, so an older copy elsewhere does not bring it back; pairing again clears it. A contact's ping never carries contacts and none is sent to a contact. Tested: unit (`a_person_s_installs_share_contacts_removals_and_revocations`: learned, the later nickname wins either way, a removal travels and a stale copy does not undo it, a third install and its revocation travel; `only_the_person_s_own_installs_sync_and_only_well_formed_contacts`); `castcorder-app/tests/presence.rs` (`a_person_s_installs_share_contacts_through_the_rendezvous`: a second install linked after pairing learns Bob, Bob sees both installs online, a nickname and a removal reach the first install).
- **App installs only.** A browser profile holds no person key and no mailbox, so it neither makes nor answers contact requests. An install with contacts does not link itself to another person: they paired with its current person.
- **One-sided states.** Removing a contact is local: the other side is not told and keeps listing you, but your install stops answering its presence pings, so it sees you offline ("Presence" below). If the accepting answer is lost, only the maker lists the other until they pair again.
- **Room trust for a person.** On a room's card the host machine picks a contact to trust (`POST /rooms/trust`; only a contact can be picked, anyone can be dropped). The room saves the person id (`room.json` `persons`); any device whose offer carries a certificate of that person, for the key that signed the offer, is a trusted device in the room, decided per offer: it enters when the room is locked and can be granted the producer role. Taking it back ends that, except for a device that also joined with a producer present, which is trusted on its own. Removing the contact leaves the room's trust as it is: being a contact grants no room access, and ending one takes none away. Status queries do not count person trust yet (cast-40e.11).
- **From a call (cast-40e.10).** The host tells everyone in the call each participant's person, as its certificate names it and the host verified it (`ParticipantName::person`; the host machine stands for the host's own person). In the People panel, "Add as contact" shows on a participant linked to another person when this page can act for its install: the page asks its install for a contact code made for that person (`POST /contacts/code {"person"}`, `Contacts::new_code_for`) and sends it (`Request::OfferContact`, the code's first link). The host passes it on (`Event::ContactOffer`) only between two joined participants of different persons and only a code that parses as one; an anonymous participant can neither offer nor be offered. ## Presence

Contacts see which of each other's app installs are online (ADR 0005, cast-40e.3; castcorder-host `presence`). It needs no new service: each install's host key is already a rendezvous mailbox, so a ping is one more sealed offer kind through the same mailbox, on the Rust rendezvous and the Worker alike (castcorder-mailbox is unchanged).

- **A ping.** `OfferPlain::presence` (`{"device": NAME}`), sealed to one of the contact's install keys from `contacts.json`, with a fresh nonce in `sdp`, a proof signed by this install's key for that install's id, this install's certificate in `cert` and the person's name in `name`. It goes out as a guest connection naming that mailbox (`?mailbox=`, so it never mints relay credentials) and waits at most 10 s for the answer.
- **Only contacts are answered.** The install checks the proof and that the certificate is an app install's, for the very key that signed, of a person in its contacts; then it answers `AnswerPlain::Presence` (its person name and device name). A stranger, a removed contact, or anyone while it appears offline gets no answer at all, which looks like an install that is not running. Both sides learn: the asker that the answerer is online, the answerer that the asker is. A ping from another app install of a contact's person (certified by the person key the contact was paired with) is answered, and that install is kept as one of theirs and pinged too.
- **What "online" means.** The app is running, holds its rendezvous connection, and does not appear offline. Whether it is in a call is not told. "Syncing with you" is not shown yet (see "Contact links").
- **When.** Every contact install after each registration with the rendezvous (start, reconnect) and when a contact is added; while the home is visible (`GET /contacts?look=1`, which the Contacts card sends only while the page is visible and focused), every install at most every 10 minutes. Otherwise an install shown online is pinged every hour unless heard from since (its own pings count), and one not online every 2 hours (it pings us when it starts anyway). What was heard holds for 125 minutes; a ping without an answer (`host_offline` at once, or silence) ends it at once, keeping the last-seen time. So does a leaving ping (`PresencePing.leaving`, cast-40e.12): an install that stops, or starts to appear offline, pings the installs it shows online once to say so (stopping waits at most 3 s for them), so a clean quit shows at once and the sweeps can be rare; only a crash, a lost network or a sleeping machine waits for a sweep or the stale time. A ping refused by the rendezvous's rate limit teaches nothing. The state is in memory: after a restart nothing is known until the first sweep.
- **Appear offline.** A checkbox on the Contacts card (`POST /contacts/presence {"appear_offline":B}`, kept in `contacts.json`): no pings out and none answered. The rendezvous connection stays, since the install also hosts its rooms.
- **Privacy.** The contents are sealed; the rendezvous sees which keys are online and who pings whom, the metadata ADR 0005 accepts. The mailbox's `host_offline` error already tells anyone holding an install's key (it is in that install's call links) whether it is registered. Presence adds nothing a stranger can learn, but for the same reason "appear offline" (silence) can be told from "not running" (`host_offline`) by someone holding a call link of that install.
- **Cost on the Worker.** One ping is one Worker request (the WebSocket upgrade), one Durable Object request (the connection) and two incoming WebSocket messages (the offer, the answer; billed at 20:1), about 1.1 billed Durable Object requests; the object hibernates between messages, and an idle hibernatable object is not billed for duration. An install with C contact installs, running 8 hours a day, sends about C x (7 heartbeats + 2 registrations + 6 home sweeps for an hour of looking at the home + 1 leaving) pings a day, fewer when the other side's pings spare heartbeats: with C = 10, about 160 pings, so 160 of the free tier's 100,000 Worker requests a day and about 175 of its separate 100,000 Durable Object requests, on the order of 600 such users (cast-40e.12; it was about 500 pings and 180 users with a 2-minute home sweep and a 30-minute heartbeat). The home sweeps only while its page is visible and focused, since the app hides its window to the tray and a hidden webview may still report itself visible; without that, a home left open would sweep every 10 minutes all day (about 480 pings a day for C = 10). Metering: each install counts the pings it sends, how many were answered and the pings it receives since it started (`presence_traffic` in `GET /contacts`) and logs them hourly ("presence traffic"); the Worker's own request counts are on the Cloudflare dashboard. Past that scale the next steps are the paid plan (10 million requests a month included) or a presence service that batches a person's contacts in one connection.
- **UI.** The Contacts card shows "Online on DEVICE" or "Offline, seen N min ago" beside each contact (nothing without a rendezvous) in the existing small muted style; how it should look is for the design session (cast-d2o).
- **Tested.** Unit: the board (nothing before registering, sweeps, heartbeat and retry, being pinged spares the heartbeat, the home's floor, staleness at its boundary, an unanswered ping, the counts, a leave told once, and the default timing's pings to one install over a modelled day: 13, where the old timing sent 44) and, through the real seal, a contact answered with both sides learning; a contact's leaving ping showing it offline at once (a stranger's changing nothing), and stopping or starting to appear offline telling the installs shown online once; a stranger, a wrong certificate, a stale proof, appearing offline (kept across a restart) and a removed contact unanswered; another install of a contact's person answered and kept, a browser certificate not; a revocation in a ping (one signed by another person ignored) or in an answer drops that install, and its pings and contact links are refused after. Wire shapes. `castcorder-app/tests/presence.rs`: two app installs on a real Rust rendezvous, timing shortened to seconds, see each other online after pairing, through appear offline and back, a stop (shown offline as soon as it returns) and restart, and a one-sided removal seen from the removed side. The system tier (`browser-test/lib/contacts.mjs`, also run against the Worker under `wrangler dev`) waits for "Online on" on the home and toggles appear offline.

## Contact links

A contact link is an on-demand connection between two contacts' app installs (ADR 0005, cast-40e.4): the sync-only connection's wire contract (WebRTC, the two data channels alone, no media), opened by one install to another when it has something to ask, and closed when idle.

- **Opening (castcorder-host `contact_link`).** Only to an install shown online (see "Presence"). The opening install makes a sync-only offer with a Rust dialer (castcorder-transport `dial`) on a fresh UDP socket, offering its LAN addresses as host candidates and no relay candidate of its own, and seals it to that install's key like a presence ping: `OfferPlain::contact_link`, its certificate in `cert`, a proof signed by its key over the SDP. It goes through the rendezvous mailbox (`?mailbox=`, so no relay credentials are minted for it) and waits at most 10 s for the answer. One link per install is kept while in use, on one thread; an offer and its answer run on a short-lived thread so a slow rendezvous never stalls open links.
- **Admitting.** The answering install checks it exactly as a presence ping (an app install's certificate, for the very key that signed, of a current contact's person; never while it appears offline) and otherwise does not answer at all. The offer also counts as hearing from that install. The host thread then accepts it beside whatever is live (`Host::accept_sync`): like a sync-only connection it is not a participant and is never counted as anyone in a call.
- **What it carries now.** `Request::SharedRooms`, answered with `Response::SharedRooms`: the answering install's rooms that the asking contact shares, meaning those its install was in (not kicked) and those that trust its whole person. Each says whether it is live, whether another room is live (busy), who is in the live call, and the room's call link where the contact is trusted (its install, or its person). Rooms are read as saved, never loaded. Every other request is refused. Track delivery and moving the lobby's status queries onto contact links are left for later (the app's outbox lives in its call window page, which already delivers over its own sync-only connection); invites are cast-40e.5.
- **Closing.** The opening side closes a link after 60 s with nothing asked; the answering side after 60 s without a request. Either side going away (bye, heartbeat timeout) ends it.
- **Home.** Each contact on the Contacts card has "Shared rooms" (`GET /contacts/rooms?person=ID`, the host machine's own page only), which asks every install of theirs shown online and shows the rooms in one line, in the existing small muted style.
- **Cost.** A link costs one sealed exchange through the rendezvous (about the cost of a presence ping) and no TURN allocation from the opening side; it is opened only when the home asks.
- **Tested.** Transport: a dialer against the real host's `accept_sync` on loopback, a request round trip on "control", bulk bytes on "data", bye. Unit, through the real seal: a contact's install admitted (and seen online); a stranger, another person's certificate, a browser profile, appearing offline, a presence ping and a removed contact not. `castcorder-app/tests/contact_link.rs`: two app installs on a real Rust rendezvous and a real link between them; a room that trusts the asking person is shared with its call link and another room is not, the same link answers again, trust taken back shares nothing, and appearing offline leaves no install to ask.

## Invites

A contact invites you to their call (ADR 0005, cast-40e.5; castcorder-host `invite`). An invite names who sends it, the room, its call link and who is in the call; it grants nothing, and the room's normal join rules apply.

- **Sending.** On the home, a room's ... menu > "Invite to a call now..." lists the contacts with Invite (`POST /contacts/invite {"person","room"}`). The invite is queued for that person and sent over a contact link (`Request::Invite`, answered `Done`) to each of their installs shown online; an install that is offline gets it when next seen online (presence), while the invite is under 3 hours old. A failed delivery to one install is tried again after 30 s. Inviting the same person to the same room again replaces the old invite. A room needs a call link through the rendezvous to be invited to. The card says Online, Offline, "Gets it when back online" or Invited.
- **Receiving.** Only over an admitted contact link (a current contact's app install); the link must be a call link (`http(s)` with a call link fragment). The home shows it above everything (`GET /contacts` `invites`) as "NAME invites you to ROOM" with who is in the call, Dismiss (`POST /contacts/invite/dismiss {"id"}`) and Join, which opens the app's call window on that room's lobby (the `castcorder://` form of the link). A newer invite from the same person for the same link replaces the older; invites go after 3 hours or when the contact is removed.
- **The app.** A new invite brings the home window to the front, and the tray's status line and tooltip name the newest one. Invites live in memory: a restart forgets them both ways.
- **Tested.** Unit: the queue (waits for an install online, sent once to each, retried after a failure, stale after 3 hours, replaced, dismissed, forgotten with the contact); through the real seal, an invite shown only from a contact and only with a call link (a `javascript:` link with a call link fragment refused). `castcorder-app/tests/contact_link.rs`: Ann invites Bob, it reaches his install with her room's call link and shows as delivered; while Bob appears offline a new invite waits, and he gets it when back online. The system tier (`contacts.mjs`) sends one from the home's room menu through the mailbox and sees "Invited".

## Devices

Each participant has one live source per kind and a set of recorded sources (cast-94c; castcorder-client `app/devices.rs`).

- **Picking.** The lobby has a Microphone, Camera and Speakers picker ("System default" first; Speakers only where the browser has `setSinkId`), remembered per browser profile (localStorage `castcorder.devices`: per kind the device id and name; a device whose id changed is found again by name, and one the browser does not list is kept as picked). A browser that names no device before one is allowed (Firefox) offers "Show device names", which opens the microphone and camera for a moment. That offer sits below Join and its space is kept from the first draw: the browser says whether it names devices only after the lobby is drawn, and the lobby centres its form, so a row appearing anywhere would move Join from under a click. With nothing picked the constraints are what they always were, and a picked device that is gone falls back to the default.
- **Live and recorded.** The picked microphone is the live source the others hear and also the main recorded source (`mic`); the picked camera is the live video. The in-call Devices dialog (dock button `#devices`) separates the two: Live (microphone, camera, speakers) and Recorded on this computer (the main track and any backup microphones). On the host machine's own page it also holds the native microphone panel.
- **Switching mid-call.** The new device is opened first, so one that is refused changes nothing. A microphone switch swaps the audio sender's track (`replaceTrack`: no renegotiation, mute kept); a camera switch reopens the camera on the same video sender. Mid-take a microphone switch ends the main track's segment and continues it in a new segment on the new device, exactly as after a dropout, but acknowledged as recording throughout (no Mic lost). Decided so because a different device can bring a different sample rate or channel count, which one WAV and one timing file cannot hold; each segment has one device's audio and its own timing metadata, and its sidecar names the device (`sourceLabel`), so the source id names the role (`mic`) and the sidecar names the device. A camera switch mid-take likewise ends that video track and starts a new one.
- **Backup microphones.** "Add backup microphone" records another input as its own recorded source (`mic-2`, `mic-3`, ...), never live: opened raw like the main microphone, through a storage worker of its own (`crate::worker` named `backup`: it reads its source and writes its track, writes no log files and never scans or offers; the storage worker offers its finished tracks like any other, so they land as `takeNN_<who>_mic-2.wav` with sidecar and timing). It acknowledges per take like the main microphone. Added mid-take it records from then on; removed mid-take its segment is closed first. Backups are per call: Leave closes and drops them.
- **Cannot record.** A backup that cannot be opened or recorded here (Firefox has no MediaStreamTrackProcessor and gets the AudioWorklet path, a device may be busy) stays listed as unavailable; the page warns that its main microphone still records, and at each take start (or at once mid-take) it acknowledges the source Unavailable and reports `ProfileUnmet` to producers. The take goes on.
- **Producers' remote sources (cast-swn).** Producers may see and change any participant's sources (decided 2026-11-15; device names were already disclosed at join). Each device reports its sources after every join and whenever they change (`Request::DeviceSources`: the microphones and cameras its browser lists, the picked ones, the live microphone's name, whether the camera is on, and each backup with its state); the host keeps each joined participant's latest and sends them all to producers only (`Event::DeviceSources`, on change and checked every half second, as roles change). In the People panel each other participant's row has a Devices fold with a Microphone and a Camera picker, the backups (each with Remove) and "Add a backup...". A change is `Request::ChangeSource`, which the host authorizes as a producer action and relays only to that participant's device (`Event::ChangeSource`, with the producer's name). The device applies it as if picked in its own Devices dialog (the same `pick`, `add_backup` and `remove_backup`, so the pick is remembered there too) and says so in a call note ("Ann (producer) switched your microphone to ..."; a later change of the same kind replaces the note). A device id the browser does not list is ignored with a warning. The host machine's native microphone is not offered (cast-1xd).
- **Tested.** Unit: backup track names, the call note for a producer's change. App (`castcorder-app` `tests/remote_sources.rs`, real host and guests): a producer is told a guest's sources and changes, a guest is not; changes reach only the target, with the producer's name; a guest's change and an unknown participant are refused; a leaver's sources are dropped. Browser (`lib/devices.mjs`, Chromium, Chromium without page MediaStreamTrackProcessor (backups on the AudioWorklet path) and Firefox, a host of its own): lobby picks survive a reload (Firefox through "Show device names"); the dialog shows them; the producer sees the guest's picked microphone by name in People, adds the guest's backup there and (Chromium) switches its microphone mid-take there, and the guest is told each and every participant's audio plays through the picked speakers; a backup added before the take records beside the main microphone; a mid-take microphone switch keeps the same connection, stays connected, X still hears Y, and the main track lands as two verified segments named for their devices in order, the second starting after the first ends, each on the host timeline; the backup lands as its own verified track with timing; each segment and the backup are aligned as tracks of their own; a backup whose device is refused is listed unavailable, warned and reported to producers; Leave releases every device.
- **Open.** The host machine's native microphone switching mid-call and native backups (cast-1xd). In Chromium a picked microphone on an HTTPS page sometimes gives the page MediaStreamTrackProcessor no audio at join, so capture falls back to the AudioWorklet path (cast-nbq). The fake devices share one format, so segments of different formats are untested (each segment is aligned as a file of its own).

## Not in v1

Screen sharing, text chat, live streaming to platforms, editing or mixing, mobile apps, scheduling UI, S3 targets, continuous upload during takes, explicit device pairing, self-served browser client, code signing. Host markers during a take are the first candidate after v1.
